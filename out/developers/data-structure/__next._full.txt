15:T7d00,<h2 id="overview-and-integration-status">Overview and integration status</h2><p>This document describes the <strong>outgoing UBL-style invoice JSON structure</strong> produced by DigitalInvoice&#39;s PHP <code>firsUblPayload</code> adapter and checked by its local preflight validator. It covers standard B2B invoices, simplified B2C invoices, credit notes, line details, tax and payment amounts, classification codes and database traceability. The model is based on the <strong>NRS MBS invoice-schema v1.1 profile</strong> used by DigitalInvoice.</p>
<aside class="docs-callout" data-tone="warning" aria-label="Local schema — not an official NRS schema"><strong class="docs-callout-title">Local schema — not an official NRS schema</strong><div><p>The downloadable JSON Schema is <strong>DigitalInvoice&#39;s own Draft 2020-12 projection</strong>, not a schema exported or certified by NRS. The JSON samples are fictional <strong>generated unit-test fixtures</strong>, not accepted submissions, real customer invoices, NRS-issued IRNs or evidence of clearance. The final NRS specification, official reference data and remote validation remain authoritative.</p>
</div></aside><p>The adapter and local validation are implemented, but <strong>Teecoms does not yet hold an NRS MBS licence</strong>. Live NRS submission is disabled and no production acceptance, signing or QR response is represented by these files. The <a href="/developers/api/">API reference</a> explains the separately authenticated ERP integration API, which is not an NRS submission API.</p>

buyer parties</h3><p>Each party contains <code>party_name</code>, <code>tin</code>, <code>email</code>, optional <code>telephone</code> and <code>business_description</code>, and a <code>postal_address</code> object with <code>street_name</code>, <code>city_name</code>, <code>postal_zone</code>, <code>lga</code>, <code>state</code> and <code>country</code>. The local JSON Schema requires the <strong>presence</strong> of the name, TIN, email and postal address keys. Some properties accept JSON <code>null</code> in the schema, while the PHP preflight rejects missing values or, for a B2C buyer&#39;s TIN/email, records a warning. This distinction matters: <strong>JSON Schema validity alone does not establish preflight readiness</strong>.</p>
<p>Supplier details come from <code>organizations</code> and <code>organization_compliance_profiles</code>. Buyer fields use invoice snapshot columns, including <code>customer_city_snapshot</code>, <code>customer_nrs_postal_zone_snapshot</code>, <code>customer_nrs_state_code_snapshot</code> and <code>customer_nrs_lga_code_snapshot</code>. The current invoice extraction <strong>does not fall back to changed customer master data</strong> for missing historical address codes.</p>
<h3 id="invoice-lines-classifications-and-unit-prices">Invoice lines, classifications and unit prices</h3><p>Each <code>invoice_line[]</code> contains <code>id</code>, <code>invoiced_quantity</code>, <code>line_extension_amount</code>, <code>discount_amount</code>, <code>fee_amount</code>, <code>item</code>, <code>price</code> and line-level <code>tax_total</code>. The <code>item</code> object includes a name, description and seller&#39;s item reference; <code>price</code> contains <code>price_amount</code>, <code>base_quantity</code> (currently <code>1</code>) and <code>price_unit</code>.</p>
<p>A <strong>goods</strong> line includes <code>hsn_code</code> and <code>product_category</code>; a <strong>service</strong> line includes <code>isic_code</code> and <code>service_category</code>. The adapter sets the classification-code key based on the stored goods/service type and NRS classification snapshot. The current local invoice extraction does not supply the corresponding <code>product_category</code> or <code>service_category</code> values; consequently, its strict PHP preflight can block otherwise populated lines. The downloadable fixtures deliberately supply fictional classification values so the adapter&#39;s structure can be tested, not to claim valid NRS resource codes.</p>
<h3 id="tax-totals-and-monetary-totals">Tax totals and monetary totals</h3><p>The adapter creates a <code>tax_total</code> entry holding <code>tax_amount</code> and <code>tax_subtotal[]</code>; each subtotal has <code>taxable_amount</code>, <code>tax_amount</code> and <code>tax_category</code> (<code>id</code>, <code>percent</code>). The tax subtotals are grouped by the category identifier and rate from the invoice-line snapshots. Line tax amounts and taxable amounts are based on persisted post-discount figures.</p>
<p><code>legal_monetary_total</code> includes <code>line_extension_amount</code>, <code>tax_exclusive_amount</code>, <code>tax_inclusive_amount</code> and <code>payable_amount</code>. Current <code>payable_amount</code> matches the full document total; it does not subtract payments already recorded against the invoice.</p>

<h2 id="nrs-v11-specification-update-crosswalk">NRS v1.1 specification update crosswalk</h2><p>The official <a href="https://einvoice.nrs.gov.ng/changelog">NRS API changelog</a> records <strong>April 2026</strong>, <strong>February 2026</strong> and <strong>December 2025</strong> additions relevant to this projection:</p>

Our published schema is a <strong>local snake_case adapter</strong>, not an official NRS-issued JSON Schema. Its <code>payment_status</code> enum can include <code>REJECTED</code>, but the current adapter only emits <code>PAID</code>, <code>PARTIAL</code> and <code>PENDING</code> from payment records. Schema acceptance is not proof of application workflow coverage.</p>
<p>The <a href="https://einvoice.nrs.gov.ng/serivce-providers/system-integrators">NRS System Integrator requirements</a> and <a href="https://einvoice.nrs.gov.ng/docs/system-integrator/invoice-schema?version=1.1">invoice schema documentation</a> remain authoritative for signing, SI/APP responsibilities and reference-code changes. DigitalInvoice tracks the current v1.1 specifications and updates its local payload mapping as NRS publishes changes.</p>
<h2 id="phase-5-official-code-preflight-separate-from-monetary-checks">Phase 5 official-code preflight — separate from monetary checks</h2><p>The new <code>official_code_preflight</code> readiness result performs an <strong>offline comparison</strong> of the prepared invoice against code lists whose cache status is <code>synced</code> from an authenticated NRS sandbox response. It checks invoice type, document currency, payment means, supplier and buyer state/LGA, each invoice-line quantity code, goods HS or services classification, and tax category IDs. Missing classifications and manually entered codes do not count as official verification.</p>
<p>This validation is in addition to, not a replacement for, the local JSON Schema and integer-kobo financial reconciliation below. Only approved B2B/B2C invoice snapshots that pass both local UBL checks and this official-code preflight can be <strong>offered to the separate permission-controlled sandbox <code>/validate</code> operation</strong>. An external sandbox request requires authorised credentials and compliant invoice identifiers; no successful NRS sandbox response is included in these downloadable fixtures.</p>
<aside class="docs-callout" data-tone="warning" aria-label="Issued invoice identifiers are immutable business evidence"><strong class="docs-callout-title">Issued invoice identifiers are immutable business evidence</strong><div><p>The local application may issue invoice numbers such as <code>INV-000001</code>, which do not meet the current IRN component check. Phase 5 blocks them instead of removing punctuation. A collision-safe, persisted NRS alias/numbering design and official acceptance testing remain outstanding; do not rewrite issued invoice numbers in sample mappings.</p>
</div></aside><h2 id="validation-and-kobo-reconciliation">Validation and kobo reconciliation</h2><p>The PHP preflight <code>firsUblValidate</code> checks identity and format fields, party details, structured addresses, line quantities, goods/service classification, tax categories, credit-note original references and financial equality. The downloaded JSON Schema separately checks structural types, allowed values, object properties and numeric constraints. <strong>Both checks are local. Neither calls NRS.</strong></p>
<h3 id="financial-equality-rules">Financial equality rules</h3><p>All persisted monetary values are decimal amounts with two fractional digits. The adapter converts them to <strong>integer kobo</strong> for arithmetic and equality checks, then emits JSON numeric amounts. The principal rules are:</p>
<ol>
<li><strong>Line extension</strong> = line gross amount − line discount. The header line extension equals the sum of the invoice-line extensions.</li>
<li><strong>Invoice-level discount</strong> becomes a separate <code>allowance_charge</code> item with <code>charge_indicator: false</code>; it is not deducted twice from each line.</li>
<li><strong>Tax-exclusive total</strong> = sum of line extensions − invoice-level discount.</li>
<li><strong>Tax-inclusive total</strong> = tax-exclusive total + the header tax amount; the current <code>payable_amount</code> equals this tax-inclusive total.</li>
<li><strong>Tax reconciliation:</strong> header tax = sum of line taxes = sum of the tax-subtotal amounts. Tax subtotals are grouped by code and rate.</li>
<li><strong>Database reconciliation:</strong> when original local amounts are supplied, the emitted totals are compared to the document&#39;s persisted subtotal, line discount, header discount, net and total fields.</li>
</ol>
<p>The values below are taken from the unmodified <strong>generated two-level-discount fixture</strong>, not hand-authored invoice data:</p>
<div class="docs-table-scroll" role="region" tabindex="0" aria-label="Scrollable data table"><table><thead><tr><th>Amount (fictional NGN)</th><th style="text-align:right">Fixture value</th></tr></thead><tbody><tr><td>Line gross</td><td style="text-align:right">300.00</td></tr><tr><td>Line discount</td><td style="text-align:right">20.00</td></tr><tr><td><code>line_extension_amount</code></td><td style="text-align:right">280.00</td></tr><tr><td>Invoice-level allowance</td><td style="text-align:right">50.00</td></tr><tr><td><code>tax_exclusive_amount</code></td><td style="text-align:right">230.00</td></tr><tr><td><code>tax_total[0].tax_amount</code></td><td style="text-align:right">17.25</td></tr><tr><td><code>tax_inclusive_amount</code> and <code>payable_amount</code></td><td style="text-align:right">247.25</td></tr></tbody></table></div><p>The local number parser rejects monetary text with more than two fractional digits; line quantity is stored at up to four fractional digits. Do not independently recompute tax from rounded display values if the persisted per-line amounts are authoritative.</p>

</div></aside><h2 id="known-limitations-before-production-go-live">Known limitations before production go-live</h2><ul>
<li><strong>Licensing and sandbox evidence:</strong> the MBS production gate remains closed. Authenticated sandbox catalogue sync and <code>/validate</code> code paths exist, but successful provider responses are not evidenced here; NRS-issued IDs, official lists and validated IRNs must not be invented.</li>
<li><strong>Goods and services:</strong> category fields required by the PHP preflight are not yet populated in <code>firsLocalInvoicePayload</code>; implement and test a verified data source before live submission.</li>
<li><strong>Credit notes:</strong> the preview uses the source invoice&#39;s IRN if available but currently may not populate the original invoice&#39;s issue date in <code>billing_reference</code>, because it reads a non-existent <code>credit_notes.invoice_date</code> field. Verify and correct this in the backend before production submission; fixture completeness does not resolve it.</li>
<li><strong>Older invoice snapshots:</strong> missing historical buyer location codes remain unavailable rather than falling back to current customer data. Reconcile historical records using auditable source evidence.</li>
<li><strong>Authoritative acceptance:</strong> Phase 5 checks only officially fetched code lists and offers sandbox validation; actual sandbox interoperability, remote schema changes and NRS response semantics must be tested with authorised credentials, without treating success as clearance.</li>
</ul>
