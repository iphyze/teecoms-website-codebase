6:T462d,<h2 id="scope-and-deployment-status">Scope and deployment status</h2><p>DigitalInvoice is a multi-organisation invoicing application. Its browser-based React interface communicates with a PHP API backed by a relational database. It includes invoices, approvals, credit notes, payments and supporting documents. A separate, scoped ERP integration API and outbound webhook service allow authorised business applications to read records and receive event notifications.</p>
<aside class="docs-callout" data-tone="info" aria-label="How to read the diagrams"><strong class="docs-callout-title">How to read the diagrams</strong><div><p><strong>Implemented</strong> indicates a path or control present in the reviewed application source, not independent verification of a live deployment. <strong>Sandbox-gated</strong> indicates an optional NRS request path which requires explicit server-side approval and authorised credentials. <strong>Future / licence-gated</strong> indicates a process described by the MBS model which is <strong>not</strong> an enabled production transport in DigitalInvoice. Sequence diagrams of NRS exchanges are target workflows, <strong>not</strong> evidence of successful clearance, signing, transmission or receipt.</p>
</div></aside><p>The diagrams are public system-design overviews. They intentionally omit credentials, private network addresses, infrastructure topology, internal file paths and customer records. They are based on the DigitalInvoice service and document generator, including <strong>Phase 5 changes reviewed 13 November 2026</strong>. Hosting provider, geographical data location and independent production verification remain unconfirmed.</p>
<h2 id="layered-system-and-trust-boundaries">Layered system and trust boundaries</h2><figure class="docs-diagram"><a class="docs-diagram-light" href="/docs/diagrams/digitalinvoice-system-architecture-v1.0.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Layered DigitalInvoice system architecture: browsers, PHP API, database, ERP applications, third-party providers and licence-gated NRS service"><img src="/docs/diagrams/digitalinvoice-system-architecture-v1.0.svg" alt="Layered DigitalInvoice system architecture: browsers, PHP API, database, ERP applications, third-party providers and licence-gated NRS service" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><a class="docs-diagram-dark" href="/docs/diagrams/digitalinvoice-system-architecture-v1.0-dark.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Layered DigitalInvoice system architecture: browsers, PHP API, database, ERP applications, third-party providers and licence-gated NRS service"><img src="/docs/diagrams/digitalinvoice-system-architecture-v1.0-dark.svg" alt="Layered DigitalInvoice system architecture: browsers, PHP API, database, ERP applications, third-party providers and licence-gated NRS service" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><figcaption>Layered DigitalInvoice system architecture: browsers, PHP API, database, ERP applications, third-party providers and licence-gated NRS service</figcaption></figure><p>The <strong>browser boundary</strong> separates end-user devices from the application API. Browser requests use HTTPS in production and protected session cookies, with CSRF checks for state-changing operations. The <strong>integration boundary</strong> separates external ERP clients, whose short-lived bearer tokens are scoped to one organisation, from browser sessions. The <strong>data boundary</strong> encloses the API&#39;s database access, organisation-scoped records, audit events and selected AES-256-GCM-encrypted secrets. The <strong>third-party boundary</strong> covers external services: Google identity verification, Paystack payment processing, email delivery and approved webhook receivers. The <strong>NRS boundary</strong> is separate and remains licence-gated for production.</p>

system creates, approves and locally validates invoices and can prepare a UBL-style JSON projection. <strong>Phase 5 adds authenticated sandbox reference synchronisation, official-code checks and an explicit approved-invoice sandbox <code>/validate</code> request.</strong> The NRS client also defines sandbox-only operations for signing, confirmation and transmission, but <strong>there is no connected production orchestrator</strong> linking an approved invoice to a licensed B2B clearance process.</p>
<p>In the target B2B flow, an approved invoice is validated against business data and reference codes; an authorised service submits the structured document for NRS validation and signing; an authenticated response supplies IRN, CSID and QR evidence; the invoice is confirmed and delivered to the buyer; and the relevant transmission/acknowledgement steps are completed in accordance with the authorised MBS role. These steps are <strong>future / licence-gated</strong>, not current production events. DigitalInvoice does not generate or publish fake official evidence.</p>
<aside class="docs-callout" data-tone="warning" aria-label="Verification evidence is production-only"><strong class="docs-callout-title">Verification evidence is production-only</strong><div><p>The document renderer exposes verified IRN, CSID and QR values only when the record is explicitly confirmed in the <strong>production</strong> evidence environment, with a verification timestamp and required fields. Sandbox records and illustrative sample PDFs must never pass this production verification gate.</p>
</div></aside><h2 id="b2c-reporting-target-sequence-and-24-hour-tracking">B2C reporting — target sequence and 24-hour tracking</h2><figure class="docs-diagram"><a class="docs-diagram-light" href="/docs/diagrams/digitalinvoice-b2c-reporting-v1.0.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Target B2C reporting sequence with the local 24-hour queue timer and future NRS reporting"><img src="/docs/diagrams/digitalinvoice-b2c-reporting-v1.0.svg" alt="Target B2C reporting sequence with the local 24-hour queue timer and future NRS reporting" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><a class="docs-diagram-dark" href="/docs/diagrams/digitalinvoice-b2c-reporting-v1.0-dark.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Target B2C reporting sequence with the local 24-hour queue timer and future NRS reporting"><img src="/docs/diagrams/digitalinvoice-b2c-reporting-v1.0-dark.svg" alt="Target B2C reporting sequence with the local 24-hour queue timer and future NRS reporting" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><figcaption>Target B2C reporting sequence with the local 24-hour queue timer and future NRS reporting</figcaption></figure><p>For a simplified B2C invoice, the local queue is created at approval with a due timestamp <strong>24 hours after approval</strong>. The current CLI worker supports <strong>dry runs only</strong>: it records what a connector would attempt, produces local events and flags overdue items, but makes <strong>zero NRS network submissions</strong>. An approved B2C invoice in the local queue is therefore <strong>not</strong> proof it has been reported to NRS.</p>
<p>The future workflow requires an authorised production worker to validate and report eligible B2C invoices within the statutory reporting window, monitor acceptance, handle retries according to safe idempotency rules and alert on failures. Scheduled execution, remote acceptance and production delivery performance have not been verified. The service target in the <a href="/sla/">approved SLA</a> takes effect only after licensed NRS production go-live; it is not a description of current NRS transmission.</p>
<h2 id="buyer-qr-verification-intended-external-workflow">Buyer QR verification — intended external workflow</h2><figure class="docs-diagram"><a class="docs-diagram-light" href="/docs/diagrams/digitalinvoice-buyer-verification-v1.0.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Target buyer verification sequence using a real production QR code and the NRS MBS360 verification experience"><img src="/docs/diagrams/digitalinvoice-buyer-verification-v1.0.svg" alt="Target buyer verification sequence using a real production QR code and the NRS MBS360 verification experience" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><a class="docs-diagram-dark" href="/docs/diagrams/digitalinvoice-buyer-verification-v1.0-dark.svg" target="_blank" rel="noopener noreferrer" aria-label="Open full-size diagram: Target buyer verification sequence using a real production QR code and the NRS MBS360 verification experience"><img src="/docs/diagrams/digitalinvoice-buyer-verification-v1.0-dark.svg" alt="Target buyer verification sequence using a real production QR code and the NRS MBS360 verification experience" loading="lazy"><span class="docs-diagram-expand">View full-size diagram</span></a><figcaption>Target buyer verification sequence using a real production QR code and the NRS MBS360 verification experience</figcaption></figure><p>The MBS documentation describes a buyer scanning a <strong>genuine NRS-issued QR code</strong> using the external MBS360 verification experience. The verification result comes from the NRS service, not from a DigitalInvoice-local mock QR. DigitalInvoice&#39;s production document evidence gate is designed to prevent sandbox-only or fictional identifiers from being displayed as verified production credentials. This diagram describes the <strong>intended external verification journey</strong>; it does not imply Teecoms operates MBS360 or that current sample QR codes are verifiable there.</p>
<h2 id="phase-5-controlled-sandbox-validation-path">Phase 5 controlled sandbox validation path</h2><p>A privileged platform operator may synchronise one approved code-list catalogue at a time into the local resource cache, where only a verified provider response sets <code>synced</code>. Invoice readiness compares the approved document&#39;s frozen fields against those cached codes. An authenticated user with <code>invoices.approve</code> permission may then invoke the <strong>sandbox-only</strong> validation operation, subject to approved IDs, IRN format, UBL totals, catalogue match and configured HTTPS/credential gates.</p>
<p>The sandbox response is recorded as a <strong>redacted validation-test summary</strong>, without changing the submission queue, adding verified production evidence or signing/transmitting the invoice. Certificate checks and production activation review are separate, advisory safeguards; the production HTTP sender is not implemented. The existing sequence SVGs depict <strong>future end-to-end NRS workflows</strong>, not a Phase 5 operational clearance sequence.</p>

<h2 id="nrs-v11-protocol-and-signing-boundaries">NRS v1.1 protocol and signing boundaries</h2><p>The latest <a href="https://einvoice.nrs.gov.ng/serivce-providers/system-integrators">NRS System Integrator reference</a> documents ECDSA/JAdES signing expectations. The diagrams above depict <strong>intended post-licence flows</strong>, not proof that a local JAdES signer, an authorised APP exchange or NRS production sender has been deployed. The reviewed PHP client sends NRS <code>x-api-key</code> and secret headers only behind an approved sandbox gate; ERP OAuth clients use separate credentials. DigitalInvoice tracks NRS MBS v1.1 guidance for payment status, quantity codes and tax categories; production exchange remains subject to the licensing and testing dependencies in the <a href="/developers/timeline/">implementation timeline</a>.</p>
