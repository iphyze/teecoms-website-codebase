ERP OAuth access and outbound webhooks are feature-gated and require deployment configuration. The production API origin is distributed privately during authorised integration provisioning; a public endpoint has <strong>not been independently verified</strong>. The NRS sandbox base URL is likewise supplied only through approved configuration. <strong>Teecoms has not yet obtained an NRS MBS licence. </div></aside><h2 id="overview">Overview</h2><p>DigitalInvoice is an invoicing platform developed by Teecoms Integrated Solutions Limited. This document is for integrators and technical reviewers. It describes two <strong>separate</strong> interfaces:</p>
<ol>
<li><strong>ERP integration API (v1):</strong> OAuth 2.0 client-credentials access to <strong>organisation-scoped, read-only</strong> customer, item, invoice, credit-note, payment and local NRS-readiness information; signed outbound webhooks for selected events. This is the API intended for external ERP clients.</li>
<li><strong>Web application API:</strong> cookie-based authenticated business workflows used by the DigitalInvoice web application. These include invoice creation, approval, payments and local NRS readiness. They are <strong>not</strong> writable ERP endpoints.</li>
</ol>
<p>The ERP route descriptions reflect the DigitalInvoice integration API documented on <strong>7 November 2026</strong>; the NRS sandbox/resource sections incorporate the <strong>13 November 2026 Phase 5 changes</strong>. External sandbox acceptance and live NRS production access are separate from these API definitions.</p>

<h2 id="authentication-and-security">Authentication and security</h2><h3 id="erp-access-oauth-20-client-credentials">ERP access — OAuth 2.0 client credentials</h3><p>A workspace owner or administrator creates a named ERP client, with only the read scopes it needs. The client identifier (<code>di_...</code>) and secret (<code>di_secret_...</code>) are returned on creation; the secret is shown <strong>once</strong>. Send these using <strong>HTTP Basic</strong> to <span class="docs-method" data-method="POST">POST</span> <code>/oauth/token</code> with <code>Content-Type: application/x-www-form-urlencoded</code>, <code>grant_type=client_credentials</code> and, optionally, a space-separated <code>scope</code> subset. The response is an OAuth bearer token; include it in <code>Authorization: Bearer ...</code> on versioned ERP read requests.</p>
<p>Access tokens are opaque, hashed in storage, and valid for <strong>300–900 seconds</strong> (default <strong>900 seconds</strong>); there is <strong>no refresh token</strong> in this flow. Client revocation, secret rotation and scope changes invalidate outstanding tokens. Requests are authorised against the database-assigned organisation, active/onboarded workspace, eligible subscription and requested scope. No client-provided organisation ID is trusted.</p>

The backend does not expose public client self-registration, ERP API keys or a browser OAuth authorization-code flow.</p>
</div></aside><h3 id="web-application-sessions-csrf-and-mfa">Web application sessions, CSRF and MFA</h3><p>Browser users authenticate with password or Google Sign-In, with authenticator-based TOTP MFA where required/enabled. A successful full sign-in issues an HS256 JWT access cookie (configured default <strong>15 minutes</strong>), a rotating refresh-session cookie (configured default <strong>12 hours</strong>, subject to inactivity and absolute session limits), and a readable CSRF cookie. Session cookies are HttpOnly; the CSRF token is readable so the frontend can send it with state-changing requests. <code>Secure</code> and <code>SameSite</code> cookie attributes are set by server configuration. The browser workflow uses:</p>
<ol>
<li><span class="docs-method" data-method="GET">GET</span> <code>/auth/csrf</code> to obtain the CSRF token.</li>
<li><span class="docs-method" data-method="POST">POST</span> <code>/auth/login</code> or <code>/auth/google</code>; if MFA is required, complete <span class="docs-method" data-method="POST">POST</span> <code>/auth/mfa/verify</code> before receiving an authenticated session.</li>
<li>Send <code>X-CSRF-Token</code> with cookie-authenticated writes. <span class="docs-method" data-method="GET">GET</span> <code>/auth/session</code> reads the current session, <span class="docs-method" data-method="POST">POST</span> <code>/auth/refresh</code> renews it, and <span class="docs-method" data-method="POST">POST</span> <code>/auth/logout</code> ends it.</li>
</ol>
<p>Workspace roles and feature permissions restrict browser operations. These cookie/CSRF/MFA rules <strong>do not replace</strong> OAuth authentication for ERP clients. The backend enforces HTTPS when <code>REQUIRE_HTTPS</code> is enabled, emits HSTS on HTTPS requests and restricts permitted browser origins. Actual TLS protocol versions and the deployed certificate must be verified at the hosting layer.</p>
<h2 id="api-conventions">API conventions</h2><ul>
<li><strong>Transport:</strong> HTTPS. Browser business routes primarily accept and return JSON; the OAuth token request takes URL-encoded form data. Outbound webhooks deliver JSON.</li>
<li><strong>Standard business response:</strong> <code>{&quot;status&quot;:&quot;success&quot;, &quot;data&quot;:{...}}</code>, sometimes with <code>message</code>. Failures use <code>{&quot;status&quot;:&quot;failed&quot;, &quot;message&quot;:&quot;...&quot;}</code>. <strong>OAuth token and OAuth errors use OAuth-specific fields instead.</strong></li>
<li><strong>ERP wrapper:</strong> successful reads return <code>data.&lt;resource_key&gt;</code> plus <code>data.organization_id</code> and <code>data.api_version</code> (<code>v1</code>). A list resource includes its own <code>pagination</code> object.</li>
<li><strong>Pagination:</strong> <code>page</code> defaults to <code>1</code>; <code>limit</code> defaults to <code>20</code>, minimum <code>1</code>, maximum <code>100</code>; <code>pagination</code> includes <code>page</code>, <code>limit</code>, <code>total</code>, <code>total_pages</code>. Optional filters differ by resource.</li>
<li><strong>Dates and amounts:</strong> invoice/payment dates use <code>YYYY-MM-DD</code> and timestamps are returned as stored by the service; monetary amounts are decimal values (often serialized as strings) and accompanied by <code>currency</code> such as <code>NGN</code>. Do not assume timestamps are UTC unless specified.</li>
<li><strong>Consistency:</strong> lists are ordered by the resource service. Fetch current resource state when processing a webhook; do not infer it from an event alone.</li>
<li><strong>Idempotency:</strong> ERP v1 has <strong>no write endpoints</strong> and does <strong>not</strong> advertise an <code>Idempotency-Key</code> HTTP contract. For webhook consumers, deduplicate by delivery ID or event ID. Do not retry non-idempotent browser writes automatically without checking the resource state.</li>
</ul>

<h2 id="outbound-signed-webhooks">Outbound signed webhooks</h2><h3 id="events-and-delivery-contract">Events and delivery contract</h3><p>The implementation supports these outbound event types: <code>customer.created</code>, <code>customer.updated</code>, <code>invoice.created</code>, <code>invoice.updated</code>, <code>invoice.approved</code>, <code>credit_note.approved</code>, <code>payment.recorded</code>, <code>payment.voided</code>.</p>
<p>Events are placed in a database outbox when eligible business audit events occur <strong>and both ERP feature gates are enabled</strong>. A separate CLI worker dispatches selected events to registered <strong>public HTTPS</strong> destinations (port 443, no redirect; private, loopback and other prohibited addresses are rejected). The delivery worker is not a continuously running server process automatically started by the website.</p>
<p>The worker retries eligible failures with exponential backoff, up to <strong>8 attempts</strong>, and stops for most permanent <code>4xx</code> responses (except <code>408</code>/<code>429</code>). Delivery is <strong>at least once</strong>. Webhook consumers must deduplicate and use a scoped ERP <code>GET</code> to retrieve current state. Never interpret an event as proof of NRS submission.</p>
<h3 id="headers-and-hmac-sha256-signature">Headers and HMAC-SHA256 signature</h3><div class="docs-table-scroll" role="region" tabindex="0" aria-label="Scrollable data table"><table><thead><tr><th>Header</th><th>Purpose</th></tr></thead><tbody><tr><td><code>X-DigitalInvoice-Event</code></td><td>Event type, e.g. <code>invoice.approved</code></td></tr><tr><td><code>X-DigitalInvoice-Delivery</code></td><td>Numeric unique delivery ID (deduplication)</td></tr><tr><td><code>X-DigitalInvoice-Timestamp</code></td><td>Unix seconds used in signature</td></tr><tr><td><code>X-DigitalInvoice-Signature</code></td><td><code>v1=</code> followed by lowercase hex HMAC-SHA256</td></tr><tr><td><code>Content-Type</code></td><td><code>application/json</code></td></tr></tbody></table></div><p>Compute the HMAC using the <strong>exact raw request body</strong>, not re-serialized JSON.   const sentAt = Number(timestamp)
  if (!Number.isSafeInteger(sentAt) || Math.abs(Date.now() / 1000 - sentAt) &gt; 300) return false

<h3 id="phase-5-authorised-sandbox-reference-synchronisation">Phase 5 — authorised sandbox reference synchronisation</h3><p>Platform administrators with the <code>platform.firs.manage</code> permission can request <strong>one approved reference catalogue at a time</strong> using the existing NRS/MBS admin screen. The public ERP OAuth API does <strong>not</strong> expose this operation. Supported catalogue keys are <code>invoice_types</code>, <code>payment_means</code>, <code>tax_categories</code>, <code>currencies</code>, <code>quantity_codes</code>, <code>hs_codes</code>, <code>service_codes</code>, <code>states</code> and <code>lgas</code>. The older <code>unit_codes</code> catalogue is local-only.</p>
<p>A sync requires saved NRS sandbox credentials, an approved HTTPS sandbox origin and explicit <code>NRS_SANDBOX_HTTP_ENABLED=1</code> configuration. The backend accepts an authenticated provider response only if its HTTP/envelope status and every code entry pass checks; then it atomically records the fetched catalogue as <code>synced</code>. A manual entry remains <code>manual_seed</code>; invalid or failed provider responses <strong>preserve the existing cache</strong>. Large resources exceeding the sandbox transport&#39;s 2 MiB response limit may fail safely; successful full-catalogue synchronisation has <strong>not</strong> been independently evidenced.</p>
<h3 id="phase-5-official-code-preflight-and-sandbox-validation">Phase 5 — official-code preflight and sandbox validation</h3><p>Local invoice readiness now includes <code>official_code_preflight</code>, comparing the prepared UBL-style JSON with <strong>authenticated <code>synced</code></strong> lists for invoice type, currencies, payment means, supplier/buyer state and LGA, line unit codes, goods HS or service classification codes, and tax categories. A missing, manually seeded or mismatched catalogue causes this additional preflight to fail; it does not change existing invoice monetary calculations or approval status.</p>
<p>The separate browser-session operation <span class="docs-method" data-method="POST">POST</span> <code>/firs/sandbox-invoice-validate</code> uses <code>invoices.approve</code> permission, session/CSRF protection and an approved <strong>B2B or B2C</strong> invoice snapshot. It requires a valid NRS-issued Business ID and eight-character Service ID, an alphanumeric IRN component, successful local UBL checks and a passing official-code preflight before an authorised HTTP request to the NRS sandbox <code>/validate</code> endpoint. <strong>This endpoint has no new public UI or ERP bearer-token access.</strong> It sends real invoice details to an external sandbox; use only approved test data with the necessary authorisation.</p>
<p>Its returned summary includes <code>environment: &quot;sandbox&quot;</code>, <code>operation: &quot;validate&quot;</code>, <code>validation_response_ok</code>, and explicit <code>invoice_submitted: false</code>, <code>invoice_cleared: false</code>, <code>production_evidence: false</code> fields. A successful response is a <strong>sandbox validation test</strong>, not an IRN issuance, sign, confirm, transmit or clearance event. No production NRS evidence record or invoice submission queue state is updated.</p>
<aside class="docs-callout" data-tone="warning" aria-label="Existing invoice-number constraint"><strong class="docs-callout-title">Existing invoice-number constraint</strong><div><p>The current issued-number format may include hyphens (for example <code>INV-000001</code>); Phase 5 rejects such numbers for NRS IRN construction rather than silently stripping characters. A persisted, collision-safe NRS invoice alias and an approved reconciliation strategy are still required before these invoices can pass the sandbox request preflight.</p>
</div></aside><h3 id="signing-and-production-activation-checks">Signing and production activation checks</h3><p>The new X.509 inspection helper checks an <strong>ECDSA public certificate</strong>, supported curve, validity window and SHA-256 fingerprint. It separately reports gaps for secure HSM/KMS key custody, independent JAdES tests and certificate enrolment. <strong>No private-key signature or JAdES message is created.</strong> Production readiness checks are advisory: <code>production_submission_enabled</code> stays <strong>false</strong> even when individual prerequisites are met. The existing queue remains dry-run only.</p>
<h2 id="nrs-api-v11-changes-and-authentication-boundary-13-november-2026">NRS API v1.1 changes and authentication boundary — 13 November 2026</h2><p>The external NRS API uses <strong><code>x-api-key</code> and <code>x-api-secret</code></strong> headers as described by its <a href="https://einvoice.nrs.gov.ng/docs/authentication">authentication guide</a>. DigitalInvoice&#39;s <strong>ERP clients use OAuth 2.0 bearer tokens instead</strong>. These credential systems are separate. The supplied PHP NRS sandbox client constructs <code>POST /api/v1/invoice/validate</code> and related operations only after a strict sandbox gate. Never send NRS secrets through the public ERP API or include them in downloadable examples.</p>
<p>The <a href="https://einvoice.nrs.gov.ng/changelog">official NRS v1.1 changelog</a> includes the April 2026 <code>PARTIAL</code> payment update and quantity-code resource, February 2026 tax category additions, and December 2025 invoice kinds <code>B2B</code>, <code>B2C</code>, <code>B2G</code> and <code>G2B</code>. The supplied local adapter already maps invoice payments marked <code>partially_paid</code> to <code>PARTIAL</code> and recognises the NRS quantity-code resource. <strong>The latest backend now implements authenticated sandbox resource-sync operations and an official-code preflight, but neither a completed provider sync in deployment nor an authorised sandbox acceptance test has been evidenced. There is still no production <code>/update</code> payment sender or B2G/G2B invoice workflow.</strong></p>
<p>The NRS <a href="https://einvoice.nrs.gov.ng/serivce-providers/system-integrators">System Integrator requirements</a> describe cryptographic stamping with <strong>ECDSA</strong> and <strong>JAdES</strong> signatures. The backend has a sandbox-gated remote <code>sign</code> operation plus <strong>ECDSA certificate inspection and signing-readiness checks</strong>; it does <strong>not</strong> implement a verified local JAdES/ECDSA signer. Whether DigitalInvoice or an authorised Access Point Provider must apply specific signatures must be resolved in the licensed integration design. The <a href="https://einvoice.nrs.gov.ng/serivce-providers/system-integrators">NRS System Integrator guidance</a> remains authoritative for signing responsibilities and approved service-provider roles.</p>
<h2 id="data-structure-and-schema">Data structure and schema</h2><p>The NRS mapping derives from the backend&#39;s <strong>local UBL JSON schema, UBL adapter, generated fixtures and SQL migrations</strong>. The intended public mapping covers supplier, buyer, invoice metadata, lines, discounts, tax categories, monetary totals, payment data, and references. Values such as local <code>firs_compliance_status</code> are <strong>internal readiness fields</strong>, not evidence of NRS acceptance.</p>
<p>The versioned machine-readable schema, field mapping CSV, and B2B/B2C/credit-note examples are <strong>published</strong> at <a href="/developers/data-structure/">Data structure</a>. DigitalInvoice tracks current NRS MBS technical documentation (v1.1) and updates its payload mapping as official change notices are published. This API reference intentionally avoids inventing official NRS field names or manually fabricating a compliant UBL payload.</p>
