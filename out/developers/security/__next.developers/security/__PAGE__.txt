<h2 id="identity-and-authentication">Identity and authentication</h2><h3 id="browser-sessions-and-csrf-protection">Browser sessions and CSRF protection</h3><p>DigitalInvoice uses signed <strong>JWT access tokens</strong> within browser session cookies, paired with rotating refresh-session records. The server binds access tokens to database-backed sessions and checks expiry, account state and authentication version. Access and refresh cookies are <code>HttpOnly</code>; cookie <code>Secure</code> defaults on outside local/development mode and SameSite is configurable. Cross-site request forgery checks compare a request token against a CSRF cookie for state-changing requests. Session idle and absolute timeouts are configurable.</p>
<p>Passwords are stored using PHP&#39;s <code>password_hash</code> / <code>password_verify</code> scheme (<code>PASSWORD_DEFAULT</code>, <strong>bcrypt in the supplied PHP 8.2 runtime</strong>). Password reset flows use time-limited, hashed reset tokens; the exact algorithm can evolve with the PHP runtime. No plaintext-password retention is claimed.</p>
<h3 id="multi-factor-authentication">Multi-factor authentication</h3><p>Authenticator-based MFA implements <strong>six-digit TOTP</strong> with 30-second steps and HMAC-SHA1, corresponding to the RFC 6238 family of algorithms. Secrets are encrypted before storage using AES-256-GCM; one-time recovery codes are stored as hashes. The verifier rejects replay of already-used TOTP time steps and limits sensitive operations. MFA enforcement is enabled by default for privileged owner, administrator and platform-admin accounts (including active platform staff), subject to the configured policy start, grace period and explicit policy switches. Users who require enrolment may access only a restricted self-service set of routes until setup is complete.</p>
<h3 id="google-sign-in-and-machine-credentials">Google sign-in and machine credentials</h3><p>Optional Google sign-in verifies a Google-signed ID token server-side, including the intended client audience, and respects account linking and MFA policy. ERP integrations use a <strong>separate OAuth 2.0 client-credentials flow</strong>. The client secret and issued bearer tokens are represented by SHA-256 digests in the database, not recoverable plaintext tokens. Tokens have configurable short lifetimes (five to fifteen minutes in the reviewed code), are limited to granted read scopes and are bound to an enabled organisation. ERP bearer tokens do not grant the external NRS production write interface.</p>
<h2 id="access-control-and-tenant-isolation">Access control and tenant isolation</h2><p>Application requests apply organisation membership, user roles, permissions and subscription/feature entitlements. Protected requests check whether the user and organisation remain active and reject stale authentication versions. ERP data reads resolve organisation identity from the authenticated client token, instead of trusting a caller-supplied organisation ID. Webhook administration is restricted to organisation owners and administrators. Database queries generally use prepared SQL statements and include organisation-level constraints for affected records.</p>
<aside class="docs-callout" data-tone="info" aria-label="Important limitation"><strong class="docs-callout-title">Important limitation</strong><div><p>These are controls observed in source code. A complete tenant-isolation audit, database permission review and adversarial authorisation test in the deployed environment have <strong>not</strong> been supplied as completed evidence.</p>
</div></aside><h2 id="transport-security-and-integration-boundaries">Transport security and integration boundaries</h2><p>Production-mode API requests require <strong>HTTPS</strong> by default; secure responses include HSTS when the server recognises HTTPS (<code>max-age=15552000; includeSubDomains</code>). Other configured response headers include <code>X-Content-Type-Options: nosniff</code>, <code>X-Frame-Options: DENY</code>, <code>Referrer-Policy: no-referrer</code> and no-store cache directives. Browser CORS origins are restricted by the server&#39;s configured allowlist. The minimum TLS version, certificate renewal, edge proxy headers and actual public-site HSTS behaviour must be checked at deployment; <strong>TLS 1.2+ has not been independently proven by source review alone</strong>.</p>
<p>Outbound ERP webhooks use <strong>public HTTPS hosts on port 443</strong>, validate resolved IPv4 addresses against non-public ranges, disable redirects, and pin DNS resolution for a request. Each payload is signed using <strong>HMAC-SHA256</strong> over the timestamp and raw JSON body; downstream receivers should validate the signature and apply a timestamp tolerance to resist replay. Deliveries use database-backed outbox records with status and retry handling. Inbound Paystack callbacks require provider signature verification. The API exchanges data with configured email and payment services; provider assurances and region controls are not certified by this document.</p>
<h2 id="secrets-encryption-and-token-handling">Secrets, encryption and token handling</h2><p>Designated integration credentials and MFA authenticator seeds use <strong>AES-256-GCM authenticated encryption</strong>, with per-record nonces and authenticated associated data. The backend contains key-version and rotation utilities for these encrypted fields. Passwords are one-way hashed; ERP client secrets, bearer tokens and certain single-use tokens are SHA-256 hashed before persistence. Session cookies and scope restrictions reduce exposure of reusable credentials. The code does <strong>not</strong> establish that every database column, server disk, backup, or third-party copy is encrypted at rest.</p>
<p>The NRS sandbox client requires an explicitly enabled sandbox state, a server-allowlisted HTTPS hostname, appropriate credentials, peer-certificate verification and a server-side feature flag. Phase 5 adds <strong>single-catalogue authenticated resource synchronisation</strong> and permission-controlled approved-invoice sandbox validation, both under that gate. It does <strong>not</strong> provide a general production submission channel or accept arbitrary endpoints. Failed catalogue responses preserve the old cache. Phase 5 audit entries for readiness/sandbox operations retain digests, counts and status metadata rather than copying invoice payloads, customer PII or credentials into the API log.</p>
<h2 id="auditability-document-evidence-and-availability">Auditability, document evidence and availability</h2><p>DigitalInvoice logs relevant account, invoice, payment, subscription and integration actions with event metadata. ERP webhook events and delivery attempts have persistent outbox/history records. The NRS queue stores due times, retry-plan metadata, dry-run events and overdue markers for simplified B2C invoices. <strong>The NRS queue worker is offline-only today</strong>: dry-running does not transmit documents or generate genuine IRN/CSID/QR evidence. The PDF/document evidence adapter only exposes verified production credentials when the corresponding production confirmation record is complete.</p>
<p>Implemented data structures support audit trails, but retention duration, independent log monitoring, central SIEM, backup schedules, restore tests, incident-response drills, RPO/RTO and 24/7 operational staffing are <strong>not verified by the supplied code</strong>. The <a href="/sla/">approved SLA</a> takes effect on <strong>27 November 2026</strong>; stated service objectives are contractual commitments from the applicable commencement date, not independent evidence that the controls have already been exercised or verified.</p>
<h2 id="data-protection-and-nigerian-regulatory-alignment">Data protection and Nigerian regulatory alignment</h2><p>DigitalInvoice&#39;s privacy and security design should be assessed against the <strong>Nigeria Data Protection Act 2023 (NDPA)</strong> and applicable NRS e-invoicing requirements. Customer and invoice records can contain personal and business information, and processing must follow approved lawful purposes, appropriate access controls, processor agreements, retention policies and rights-handling procedures. This page makes <strong>no independent claim of NDPA certification or completed regulatory compliance assessment</strong>.</p>
<p>Data controller/processor responsibilities, privacy notices, international transfers, data hosting location, retention periods, backup storage, breach-notification procedures and any required regulator notifications remain subject to organisation policy, legal review and contract confirmation. The notification timetable in the <a href="/sla/">SLA</a> is a contractual requirement from its effective date; it is not evidence that an incident-response exercise has already been completed.</p>
